Problem Statement

Design and implement an immersive, real-time 3D application in Unity that delivers several distinct VR interactions (shooting, archery and free-fall flight) and a mixed-reality mode from one code base; that runs on a desktop PC, on PC VR headsets through the OpenXR standard and on a Meta Quest in passthrough; that accepts keyboard and mouse, gamepad, tracked controllers and bare-hand gestures through a single input model; and that stays within the frame-time budget of a 90 Hz headset while following established VR-comfort guidelines.

Motivation

Four practical problems motivated the project:

  1. Device fragmentation. Vendor SDKs tie an application to one headset family, and student projects often work only on the headset they were developed with. OpenXR removes most of this lock-in, but the application must still be designed so that its gameplay does not depend on a particular controller layout, or on controllers at all.
  2. Cybersickness. A mismatch between visual motion and the vestibular sense causes nausea in a large share of users (LaViola [4]). Artificial locomotion, smooth rotation, camera shake and low frame rates all make it worse. Comfort therefore has to be part of the design, not a later patch.
  3. A hard real-time budget. A headset must receive a new stereo frame every refresh. Missing that deadline produces judder, which is itself a sickness trigger. The budget is the reciprocal of the refresh rate ([[t-budget]]).
  4. Evaluating XR without a headset. Headsets are scarce in teaching labs. A project that can be demonstrated and tested on a normal PC, and whose XR code can be exercised by automated or simulated input, is far easier to evaluate, debug and present.

Scope

In scope

  • Four single-player game modes and a bonus Farm Sniper scene; two-player local co-op in the shooter
  • Desktop, PC VR (OpenXR) and Meta Quest MR builds from one project
  • Controllers (5 interaction profiles) and articulated hand tracking
  • VR comfort options, haptics and binaural spatial audio
  • Procedural generation of all models, textures, sound and levels
  • Local persistence: settings, per-mode high scores, top-10 leaderboard, lifetime statistics, death heat map
  • Automated smoke test and simulated-XR verification

Out of scope

  • Online multiplayer and online leaderboards
  • Store publishing (Meta Horizon Store, Steam)
  • Eye tracking and foveated rendering
  • Full scene-mesh understanding (furniture, walls as meshes); the MR mode uses the play-area boundary
  • A formal user study with a simulator-sickness questionnaire
  • Physically two-handed bow drawing (planned, [[ch14]])

Constraints and Assumptions

  • No physical headset was available during the ESE preparation. VR features were therefore verified with the OpenXR Mock Runtime, which exercises the real OpenXR code path but has no lenses, cameras or hand tracking. Features that depend on real sensors are labelled needs hardware.
  • The development machine has only the Windows build module installed. A Quest (Android) build requires installing Android Build Support and re-running the project's OpenXR configuration tool for the Android tab.
  • Development used Unity 6000.5.5f1 with the Built-in Render Pipeline. A custom post-processing shader replaces URP's volume system.
  • All performance figures come from the development PC (Intel Core i7-13650HX, NVIDIA GeForce RTX 4060 Laptop GPU). A mobile headset GPU is slower, so the large margin under 11.1 ms is intentional.

Expected Outcomes

  1. A playable, demonstrable project with four game modes (and a bonus scene) that runs on a standard Windows PC without additional hardware.
  2. A VR-ready build that runs on any OpenXR headset with controllers or hands, and a Quest MR mode.
  3. Measured evidence that the project meets its real-time and comfort requirements.
  4. Documentation, diagrams and screenshots that allow the system to be evaluated, maintained and extended.
